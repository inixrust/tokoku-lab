# L18.1 · Capstone: sebelum vs sesudah

**Hari 6 · kelompok · 90 menit (+ presentasi 5 menit per kelompok) · slide 155 (siklus di slide 152–154)**
**Checkpoint:** branch `capstone/broken` (mode perf, image JDK 21)

## Tujuan

TokoKu versi ini **lambat dan tidak stabil**. Temukan masalah performa yang tertanam, buktikan dengan data, perbaiki
satu per satu, lalu sajikan tabel sebelum vs sesudah.

## Menyalakan

```powershell
git checkout capstone/broken
git switch -c capstone/kelompok-<nama>          # kerja di branch kelompok
.\mvnw.cmd package -DskipTests
.\scripts\reset-db.ps1
docker compose -f infra/compose.yaml --profile db --profile kafka --profile obs --profile security --profile apps up -d --build --force-recreate --wait
.\scripts\seed-perf.ps1                          # 200.000 order alice/bob
$alice = .\scripts\get-token.ps1 -User alice
```

## Aturan main

1. **Baseline dulu**: wrk2 `-R` tetap atau JMeter open model, warm-up, **3 run**. Endpoint minimal:
   `GET /api/orders` dan `POST /api/orders` (token alice). Pilih laju yang benar-benar tercapai (cek achieved rps).
2. Setiap perubahan = **satu baris** di log eksperimen: hipotesis → perubahan → hasil
   (p50/p99/p99.9/max, CPU, heap, query/request). Template: [capstone-laporan.md](capstone-laporan.md).
3. **Satu commit per perubahan** (`git log` menjadi bukti).
4. Build ulang dan deploy ulang service yang diubah:
   `.\mvnw.cmd -pl order-service package -DskipTests` lalu `docker compose ... up -d --build order-service`.
   Perubahan migrasi Flyway: buat versi baru (jangan ubah migrasi yang sudah ada).
5. Temuan dinilai dari **bukti data** (baseline → perubahan → ukur ulang). Membandingkan kode dengan tag
   atau branch lain (`git diff`) tidak dihitung sebagai bukti.

## Alat yang tersedia

| Pertanyaan | Alat |
|---|---|
| Endpoint mana terburuk? | Grafana **TokoKu - Golden Signals** (p99 per endpoint), exemplar → trace |
| Hop / query mana yang lambat? | Tempo (trace), Loki (log, filter `trace_id`) |
| Berapa query per request? | `docker logs tokoku-order-service-1` → `JDBC statements` |
| Query lambat? | `docker compose ... exec postgres psql -U postgres -d tokoku`, lalu `EXPLAIN (ANALYZE)` |
| Thread menunggu apa? | `docker exec tokoku-order-service-1 jcmd 1 Thread.dump_to_file -format=json /tmp/t.json` |
| CPU / alokasi / pinning? | `jcmd 1 JFR.start duration=60s filename=/tmp/c.jfr`, lalu `docker cp` dan buka di JMC; `jfr print --events jdk.VirtualThreadPinned` |
| Memori? | dashboard JVM, `jcmd 1 GC.heap_info`, `GC.class_histogram`, `GC.heap_dump`, `VM.native_memory` (butuh NMT) |
| Container mati? | `docker inspect tokoku-order-service-1 --format "{{.State.OOMKilled}} {{.State.ExitCode}}"` |
| Pool? | panel HikariCP (`hikaricp_connections_pending`) |

## Target

Setiap kelompok menemukan dan **membuktikan** minimal **3 masalah** (akar masalah, bukan gejala), masing-masing dengan
data sebelum dan sesudah.

## Rubrik

| Aspek | Bobot | Indikator |
|---|---|---|
| Metodologi | 40% | Baseline valid (open model, warm-up, ≥3 run), satu variabel per ukur |
| Temuan & perbaikan | 30% | Jumlah dan kedalaman: akar masalah, bukan gejala |
| Bukti data | 20% | Tabel sebelum vs sesudah: percentile + maks, CPU, heap, query/request |
| Presentasi | 10% | 5 menit, jelas, trade-off disebut |

## Jebakan umum

- Mengubah beberapa variabel sekaligus: efeknya tidak bisa diatribusikan.
- Melaporkan rata-rata, atau memakai `-R` yang tidak tercapai (achieved rps jauh di bawah target).
- Menyimpulkan dari satu run.
