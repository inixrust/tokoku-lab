# L15.1 · N+1 dan ukuran pool

**Hari 5 · berpasangan · 45 menit · slide 133 (pola di slide 127–132)**
**Checkpoint:** `L15.1-start` → `L15.1-solution` (mode perf, lihat [mode-perf.md](mode-perf.md))

## Tujuan

Memperbaiki N+1 pada daftar order, lalu membuktikan argumen "pool kecil lebih cepat" (Wooldridge) dengan load test.
**Satu variabel per pengukuran.**

## Yang sudah disediakan

- Postgres dibatasi `cpus: 2` (compose), supaya efek ukuran pool terlihat.
- Ukuran pool order-service lewat variabel `ORDER_POOL_SIZE` (default 10), tanpa edit file:

  ```powershell
  $env:ORDER_POOL_SIZE = 50
  docker compose -f infra/compose.yaml --profile db --profile kafka --profile obs --profile security --profile apps up -d --force-recreate --wait order-service
  Remove-Item Env:ORDER_POOL_SIZE   # kembali ke 10
  ```

- `loadtest/jmeter/payments.jmx` versi lengkap (jawaban L12.2).

## Persiapan pengukuran (wajib, agar data sama untuk semua run)

## Langkah

### 1. Baseline

- Query per request `GET /api/orders` (log `Session Metrics`: `docker logs tokoku-order-service-1 | Select-String "JDBC statements"`).
- p99 dengan beban tetap (laju sama dengan L12.1 (b)); warm-up 1 menit dulu.

### 2. Dua tahap + `@EntityGraph` (slide 128)

1. Tahap 1: `Page<IdOnly> findIdsByCustomerId(String customerId, Pageable pageable)` (projection record ID saja).
2. Tahap 2: `@EntityGraph(attributePaths = "items") List<OrderEntity> findByIdIn(Collection<Long> ids)`.
3. Di `JpaOrderStore.findAllByCustomer`: gabungkan, pertahankan urutan halaman, kembalikan `PageImpl`.
4. Konfigurasi slide 129: `hibernate.query.fail_on_pagination_over_collection_fetch: true`,
   `hibernate.jdbc.batch_size: 50`, `order_inserts`, `order_updates`.
5. Build ulang (`.\mvnw.cmd -pl order-service package -DskipTests`, lalu `up -d --build order-service`), ukur ulang
   dengan beban **yang sama**.

### 3. Pool 50 vs 10

1. **Cari kapasitas dulu** (pool 10): naikkan `-R` bertahap (mis. 300, 450, 600, ...) sampai achieved rps < target atau
   p99 melonjak.
2. Uji pool **10** dan **50** pada laju ±70–80% kapasitas itu, masing-masing setelah warm-up 1 menit, **2× bergantian**
   (10, 50, 10, 50).
3. Catat p99 dan `hikaricp.connections.pending` (dashboard Golden Signals → HikariCP, atau Explore:
   `max_over_time(hikaricp_connections_pending{service_name="order-service"}[1m])`).

## Berhasil bila

- [ ] Query per request turun dari **1 + N (+1 count)** menjadi **≤ 3** (ID page + count + fetch items; 2 bila memakai
      `Slice`).
- [ ] Tabel pool 50 vs 10 berisi p99 dan `pending`, dan Anda bisa menjelaskan hasilnya dengan formula
      `(core × 2) + spindle` dan kapasitas Postgres 2 CPU.

## Jebakan umum

- Mengubah fetch plan **dan** pool sekaligus dalam satu pengukuran.
- `JOIN FETCH` collection + `Pageable`: perilakunya bergantung versi Hibernate. Hibernate 6 memotong halaman di
  memori (dengan `fail_on_pagination_over_collection_fetch` → error keras). Hibernate 7.4 menulis ulang query menjadi
  subquery dengan paging di SQL, dan bila ada filter pada collection yang di-fetch hasilnya SQL error (D15.1). Pola
  dua tahap (halaman ID + `@EntityGraph`) dapat diprediksi di kedua versi.
- Membandingkan di atas kapasitas: request menumpuk, heap 256 MiB tertekan, dan angka menjadi kacau serta tidak bisa
  diulang. Ukur di bawah kapasitas.
- Lupa reset + seed: jumlah order alice berbeda antar-run.
