# L7.1 · Saga order → inventory

**Hari 3 · berpasangan · 60 menit · slide 66 (pola di slide 58–62)**
**Checkpoint:** `L7.1-start` → `L7.1-solution`
**Infra:** `docker compose -f infra/compose.yaml --profile db --profile kafka up -d`

## Tujuan

Membuat order + outbox dalam satu transaction, relay ke Kafka, consumer idempotent di inventory, dan compensation
(`CANCELLED`) saat stok tidak cukup.

```
order-service                 Kafka                    inventory-service
POST /api/orders
 └─ tx: order PENDING + outbox ─► relay ─► [orders] ─► listener (dedup eventId)
                                                        └─ tx: reservasi stok + outbox
 listener ◄──────────── [stock-events] ◄── relay ◄──────┘  StockReserved / StockRejected
 └─ StockRejected → CANCELLED (compensation)
```

## Yang sudah disediakan

- Kafka KRaft di compose (profil `kafka`); topic `orders` dan `stock-events` dibuat otomatis saat service start.
- Migrasi `outbox` dan `processed_event` di kedua service (`order-service` V3, `inventory-service` V2).
- **order-service:** kontrak event `OrderPlaced` (topic `orders`) dan `StockEvent` (topic `stock-events`),
  port `OrderStore.updateStatus`, aturan `Order.canMoveTo(...)`, serta test `OrderOutboxKafkaTest`
  (Testcontainers Postgres + Kafka, masih `@Disabled`).
- **inventory-service:** modul `outbox-support` (`OutboxWriter`, `OutboxRelay`, `ProcessedEvents`),
  `StockService.reserve(...)` → `ReservationResult` (sealed: `Reserved` / `Rejected`),
  `StockEventPublisher` (menulis `StockReserved`/`StockRejected` ke outbox).
- `scripts/replay-event.ps1`: mengirim ulang event OrderPlaced terakhir.

Kafka record dari relay: **key** = ID aggregate (orderId), **value** = JSON, **header** `eventType` dan `eventId`.

## Langkah

### 1. order-service: order + outbox dalam satu transaction (slide 59)

- Buat entity JPA untuk tabel `outbox` (lihat `V3__outbox.sql`) dan repository-nya.
- Di `PlaceOrderService`, simpan order **dan** baris outbox `OrderPlaced` di transaction yang sama.
  Serialisasi payload dengan `JsonMapper` (Jackson 3, sudah berupa bean). `aggregate_id` = orderId.

### 2. order-service: `OutboxRelay` (slide 60)

- `@Scheduled(fixedDelay = 500)` + `@Transactional`.
- Query native: `select ... where published_at is null order by id limit 100 for update skip locked`.
- Kirim dengan `KafkaTemplate`: key = `aggregate_id`, header `eventType` + `eventId`; tunggu ack
  `.get(5, TimeUnit.SECONDS)`; lalu isi `published_at`.
- Hapus `@Disabled` di `OrderOutboxKafkaTest` dan jalankan.

### 3. inventory-service: consumer idempotent (slide 61)

`@KafkaListener(topics = "orders")` + `@Transactional`:

1. Abaikan event yang header `eventType`-nya bukan `OrderPlaced`.
2. `processedEvents.markIfNew(eventId)`; bila `false` → duplikat, return.
3. `stockService.reserve(...)`; dengan `switch` pada `ReservationResult`, panggil
   `stockEventPublisher.stockReserved(...)` atau `stockRejected(...)`.

### 4. order-service: compensation (slide 62)

`@KafkaListener(topics = "stock-events")`: `StockRejected` → order `CANCELLED`. Bonus: `StockReserved` → `CONFIRMED`.
Gunakan `Order.canMoveTo(...)` agar status final tidak berubah lagi, dan dedup `eventId` dengan tabel `processed_event`.

### 5. Uji

| Skenario | Cara | Hasil yang diharapkan |
|---|---|---|
| a. Stok cukup | order product 1 qty 2 | stok product 1 berkurang 2; order `PENDING` (bonus: `CONFIRMED`) |
| b. Stok kurang | dua order product 19 qty 2 **berturut-turut** (stok 2), lihat perintah di bawah | order pertama mengambil stok; order kedua `CANCELLED`; stok product 19 = 0 |
| c. Event duplikat | setelah (a): `.\scripts\replay-event.ps1` | log inventory "duplikat"; stok **tidak** berkurang lagi |

Cek stok: `curl.exe localhost:8083/api/inventory/1`. Cek order: `curl.exe localhost:8082/api/orders/<id>`.

Perintah skenario (b) di PowerShell:

```powershell
$body = '{"customerId":"7f2c1a4e-0b1d-4c55-9a6e-a11ce0000001","lines":[{"productId":19,"quantity":2}]}'
1..2 | ForEach-Object { curl.exe -s -H "Content-Type: application/json" -d $body localhost:8082/api/orders; "" }
```

> Mengapa dua order? Pengecekan stok sinkron dari L8.1-A masih ada (fail fast): satu order qty 5 langsung ditolak
> 409 dan tidak pernah sampai ke saga. Dua order yang dikirim berturut-turut sama-sama lolos pengecekan sinkron,
> karena stok baru berkurang setelah event diproses. Itulah eventual consistency, dan karena itulah saga tetap
> dibutuhkan.

## Jebakan umum

- Publish ke Kafka langsung di controller/service tanpa outbox (dual write).
- Lupa `@EnableScheduling`: relay tidak pernah jalan, outbox menumpuk.
- Dedup di luar transaction bisnis: bila reservasi gagal setelah `markIfNew`, event dianggap sudah diproses.

**Bonus (bila selesai lebih cepat):** dead-letter topic dengan `DefaultErrorHandler` + `DeadLetterPublishingRecoverer`.
