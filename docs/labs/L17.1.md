# L17.1 · Caffeine vs Redis

**Hari 6 · berpasangan · 20 menit · slide 146 (pola di slide 142–144)**
**Checkpoint:** `L17.1-start` → `L17.1-solution` (mode perf, lihat [mode-perf.md](mode-perf.md))

## Tujuan

Mengukur dampak local cache pada p99 dan beban, membaca hit ratio, dan melihat sendiri **stale data** antar-instance.

## Yang sudah disediakan

- `PUT /api/products/{id}` (ubah nama/harga, `@Version`) yang menerbitkan event `ProductUpdated` (in-process).
- Instance kedua product-service: compose profil **`scale`**, port **8091** / 9091.
- Redis: compose profil **`cache`** (opsional).
- `loadtest/wrk2/get-product.lua` (ID acak 1–20, header `API-Version`).
- Grafana: dashboard **TokoKu - Cache** (hit ratio, gets hit/miss, ukuran, eviction, p99 per instance).
- Bruno: `product/PUT ubah harga ...` dan `product/GET ... instance kedua (8091)`.

## Langkah

### 1. Baseline tanpa cache

```powershell
.\loadtest\wrk2\run.ps1 -Network tokoku_default -Script get-product.lua -Rate 1500 -Duration 30s -Url http://product-service:8080/api/products/1   # warm-up
.\loadtest\wrk2\run.ps1 -Network tokoku_default -Script get-product.lua -Rate 3000 -Duration 60s -Url http://product-service:8080/api/products/1
docker stats --no-stream   # CPU product-service dan postgres selama beban
```

### 2. Caffeine (slide 144)

1. Dependency `spring-boot-starter-cache` + `com.github.ben-manes.caffeine:caffeine`.
2. `@EnableCaching` di class config tersendiri (bukan class main).
3. `application.yml`:

   ```yaml
   spring:
     cache:
       type: caffeine
       cache-names: products
       caffeine.spec: maximumSize=10000,expireAfterWrite=10m,recordStats
   ```

4. `@Cacheable(cacheNames = "products", key = "#id")` pada `ProductService.get`.
5. Invalidation: listener `ProductUpdated` + `@CacheEvict(cacheNames = "products", key = "#event.productId()")`
   (sebaiknya `@TransactionalEventListener`: setelah commit).
6. Build, `up -d --build product-service`, ukur ulang dengan beban yang sama. Catat p99, CPU product-service, CPU
   Postgres, dan **hit ratio** (dashboard Cache).

### 3. Stale data antar-instance

```powershell
docker compose -f infra/compose.yaml --profile db --profile kafka --profile obs --profile security --profile apps --profile scale up -d --wait product-service-2
```

1. GET product 1 di **8081** dan **8091** (keduanya sekarang ter-cache).
2. PUT harga baru lewat **8081**.
3. GET lagi di 8081 dan 8091. Apa yang terlihat? Berapa lama 8091 stale?

### 4. Opsional: Redis

`docker compose ... --profile cache up -d redis`, lalu jalankan product-service dengan `SPRING_PROFILES_ACTIVE=redis`
(lihat `application-redis.yml` di solusi). Ulangi langkah 3: apakah masih stale? Ukur ulang p99.

## Jebakan umum

- Cache tanpa `maximumSize` dan TTL, dan tanpa mengukur hit ratio. Tanpa `recordStats`, metric hit/miss kosong.
- Mengukur di laju rendah: lookup PK yang sudah murah tidak banyak berubah p99-nya; dampak cache terlihat pada CPU
  aplikasi dan DB, serta saat mendekati kapasitas.
- `refreshAfterWrite` di `caffeine.spec` butuh bean `CacheLoader`; tanpa itu aplikasi gagal start (dibahas di D17.1).
- Redis + record domain: Java serialization gagal (`Product` bukan `Serializable`); pakai serializer JSON.
