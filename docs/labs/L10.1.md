# L10.1 · Downstream yang lambat

**Hari 4 · berpasangan · 40 menit · slide 85 (pola di slide 77–83)**
**Checkpoint:** `L10.1-start` → `L10.1-solution`
**Infra:** `docker compose -f infra/compose.yaml --profile db --profile kafka --profile obs --profile chaos up -d`

## Tujuan

Membandingkan perilaku order-service saat inventory lambat: **tanpa timeout → timeout dari data → retry (tanpa lalu
dengan jitter) → circuit breaker + fallback**. Semua diukur di bawah beban ringan, bukan dengan satu request.

## Yang sudah disediakan

- **Toxiproxy** (profil `chaos`): `localhost:18083` → inventory di host (`localhost:8083`). order-service sudah
  diarahkan ke proxy (`tokoku.inventory.base-url: http://localhost:18083`).
- `scripts/chaos.ps1`: `-Latency 3000`, `-Down`, `-Reset`, atau tanpa parameter untuk melihat status.
- `loadtest/wrk2/run.ps1` (wrk2 di Docker) + `post-order.lua`. Perintah beban yang **dipakai sepanjang lab**:

  ```powershell
  .\loadtest\wrk2\run.ps1 -Rate 50 -Duration 60s -Url http://host.docker.internal:8082/api/orders -Script post-order.lua
  ```

- `ResilienceConfig`: `CircuitBreakerRegistry` (konfigurasi slide 82) + binding metric Resilience4j ke Micrometer.
- Grafana: dashboard **TokoKu - Resilience** (state breaker, laju call ke inventory, rasio amplifikasi, p99) dan
  **TokoKu - Golden Signals**.
- Stok product 1–18 dibuat besar (`V3__restock_for_load_tests.sql`) agar stok tidak habis di tengah uji.

### 0. Baseline dan timeout dari data

1. Jalankan beban tanpa toxic. Di dashboard Resilience, panel *p99: order vs call inventory*, catat **p99 dan
   p99.9 call inventory** (atau Explore:
   `histogram_quantile(0.999, sum by (le) (rate(http_client_requests_milliseconds_bucket{service_name="order-service"}[1m])))`).
2. `.\scripts\chaos.ps1 -Latency 3000`, jalankan beban lagi dengan read-timeout lama (5 s): baris 1.
3. Tentukan `spring.http.clients.read-timeout` dari p99.9 terukur + margin. Tulis alasan angkanya di komentar.
   Restart, ukur lagi: baris 2.

### 1. Retry (slide 80)

1. Aktifkan `@EnableResilientMethods` (mis. di `ResilienceConfig`).
2. Di `InventoryStockAdapter.check(...)`: `@Retryable(includes = ResourceAccessException.class, maxRetries = 2,
   delay = 200, multiplier = 2)` **tanpa** jitter. Ukur: baris 3. Lihat panel *Laju order vs laju call ke inventory*:
   retry datang **serentak** dalam gelombang.
3. Tambahkan `jitter = 100, maxDelay = 1000`. Ukur: baris 4. Gelombangnya **tersebar**.

### 2. Circuit breaker + fallback (slide 82)

1. Ambil breaker: `circuitBreakerRegistry.circuitBreaker("inventory")`.
2. Bungkus panggilan: `breaker.executeSupplier(() -> inventory.stock(productId))`.
   **Retry membungkus breaker** (urutan slide 77): `@Retryable` tetap di method, breaker di dalamnya.
3. `CallNotPermittedException` (breaker OPEN) → fallback `Availability.UNKNOWN`: order tetap dibuat `PENDING`,
   saga L7.1 yang memutuskan stok. Exception ini **tidak** di-retry (bukan `ResourceAccessException`).
4. Ukur: baris 5. Di dashboard, amati **CLOSED → OPEN → HALF_OPEN**, lalu `.\scripts\chaos.ps1 -Reset` dan lihat
   breaker kembali CLOSED.

## Jebakan umum

- Menyalin angka timeout dari slide, bukan dari data latency.
- Menguji retry/jitter dengan satu request: perbedaan jitter hanya terlihat saat banyak request gagal bersamaan.
- Breaker tanpa timeout: call yang menggantung tidak pernah dihitung gagal (slide 77).
- `minimumNumberOfCalls` default 100: di beban kecil breaker tidak pernah terbuka.
